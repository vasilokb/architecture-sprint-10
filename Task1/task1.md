
# Контекст компании «Медикаменте»
Компания «Медикаменте» предоставляет медицинские услуги в одном офисе с 20 сотрудниками и 15 медицинскими специалистами. Все операции с данными выполняются вручную: журналы приёма пациентов, учёт платежей, медицинские карты и анализы хранятся в Excel или в виде сканов на общем диске. Учёт финансов ведётся в «1С Бухгалтерия предприятия», интегрированной с контрольно-кассовыми машинами (ККМ). Учёт товарно-материальных ценностей (ТМЦ) осуществляется в «1С Торговля и склад». Компания планирует открыть новые филиалы, ожидая пятикратного роста данных, и усилить безопасность конфиденциальных данных в соответствии с законодательством РФ.

# Анализ конфиденциальных данных
## Категории конфиденциальных данных
Конфиденциальные данные, обрабатываемые, но не учтённые должным образом в системах компании, включают следующие категории:

- **Персональные данные пациентов**:
    - Обязательные: Ф. И. О., дата рождения, телефон, электронная почта.
    - Дополнительные: адрес прописки, место работы/учёбы, хронические заболевания, паспортные данные (в договорах), СНИЛС (для налоговых вычетов).
    - Проблемы: данные из расширенной формы, паспортные данные и СНИЛС хранятся в PDF/JPG без структурирования, классификации и защиты.

- **Медицинские данные**:
    - Результаты анализов, заключения врачей, медицинские карты, история посещений, рецепты.
    - Проблемы: данные в Excel/PDF не тегированы как чувствительные, не защищены от копирования, отсутствует связь с идентификаторами пациентов.

- **Финансовые данные**:
    - Суммы платежей, даты, способы оплаты (наличные, безналичные), банковские реквизиты (номера карт, счета).
    - Проблемы: реквизиты записываются вручную в Excel или бумажные журналы, не классифицированы как конфиденциальные, не защищены.

- **Данные сотрудников**:
    - Ф. И. О., паспортные данные, СНИЛС, банковские счета, зарплатные ведомости.
    - Проблемы: данные в «1С Бухгалтерия» доступны всем бухгалтерам без разграничения ролей, не шифруются.

- **Данные лабораторных анализов**:
    - Биомаркеры, результаты тестов, идентификаторы пациентов.
    - Проблемы: Excel-файлы в «Laboratory Registry» не защищены, доступны всем с доступом к серверу, могут быть изменены.

- **Дополнительные данные**:
    - Логи транзакций ККМ (идентификаторы, суммы, Ф. И. О. пациентов).
    - Уведомления в Exchange Mail Server (Ф. И. О., даты приёма, результаты анализов, медицинские данные).
    - Договоры в PDF (паспортные данные, подписи).
    - Проблемы: отсутствие фильтрации конфиденциальных данных в email и договорах, логи ККМ не защищены, данные не классифицированы.

## Проблемы учёта
- **Хранение**: Данные в Excel, PDF, JPG на файловом сервере доступны всем с доменной аутентификацией, без ролевого контроля (RBAC/ABAC).
- **Отсутствие аудита**: Операции (чтение, изменение, копирование) не логируются, что нарушает Data Lineage.
- **Неконтролируемые потоки**: Передача данных между ККМ, «1С», Exchange Mail Server и сотрудnikami не шифруется и не проверяется на целостность.
- **Ручная обработка**: Ввод данных вручную увеличивает риск ошибок и утечек.
- **Несоответствие ФЗ-152**: Отсутствие классификации, механизмов удаления данных по запросу и шифрования нарушает законодательство РФ.
- **Отсутствие Privacy by Design**: Системы не минимизируют данные (Data Minimization) и не защищают их по умолчанию.

## Аудит мер по обеспечению безопасности данных в компании «Медикаменте»

### Требования к безопасности данных
На основе ФЗ-152, GDPR (в части применимости к лучшим практикам) и стандартов безопасности (например, ISO/IEC 27001) определены следующие требования:
1. **Конфиденциальность**: Данные должны быть доступны только уполномоченным лицам (RBAC/ABAC).
2. **Целостность**: Данные не должны быть изменены без контроля.
3. **Доступность**: Данные должны быть доступны для уполномоченных пользователей при необходимости.
4. **Аудит и трассировка**: Все операции с данными должны логироваться (Data Lineage).
5. **Минимизация данных**: Сбор и хранение только необходимых данных (Data Minimization).
6. **Шифрование**: Данные должны быть зашифрованы при хранении и передаче.
7. **Удаление данных**: Возможность удаления данных по запросу клиента.
8. **Privacy by Design**: Безопасность должна быть встроена в архитектуру систем.

### Архитектурные практики безопасности
1. **Классификация данных**: Тегирование данных по уровню конфиденциальности.
2. **Контроль доступа**: Внедрение RBAC/ABAC для ограничения доступа.
3. **Шифрование**: Использование AES-256 для хранения и TLS 1.3 для передачи.
4. **Аудит**: Логирование операций с данными в системах SIEM (например, ELK Stack).
5. **DLP-системы**: Предотвращение утечек данных (Data Loss Prevention).
6. **Сегментация сети**: Разделение сетей для разных типов данных и пользователей.
7. **Мониторинг и алертинг**: Обнаружение аномалий в доступе (например, с помощью Victoria Metrics).
8. **Регулярное тестирование**: Пентесты и анализ уязвимостей.

### Сопоставление процессов с требованиями и практиками

#### Процесс 1: Регистрация пациента на ресепшене
- **Описание**: Пациент предоставляет Ф. И. О., дату рождения, телефон, email, адрес, хронические заболевания, паспортные данные, СНИЛС. Данные вносятся в Excel (журнал записей, список пациентов) и PDF/JPG (договоры), хранятся на файловом сервере. Уведомления отправляются через Exchange Mail Server.
- **Конфиденциальные данные**: Персональные данные, паспортные данные, СНИЛС.
- **Текущее состояние**:
    - Доступ к файлам на сервере ограничен доменной аутентификацией, без RBAC/ABAC.
    - Данные не шифруются при хранении и передаче.
    - Нет аудита операций с данными.
    - Уведомления содержат Ф. И. О. и даты без защиты.
- **Соответствие требованиям**:
    - Нарушение конфиденциальности: доступ возможен для всех сотрудников.
    - Нарушение целостности: данные могут быть изменены без контроля.
    - Нарушение аудита: операции не логируются.
    - Нарушение минимизации: сбор избыточных данных без обоснования.
    - Нарушение шифрования: данные в PDF/JPG и email не защищены.
- **Соответствие практикам**:
    - Отсутствует классификация данных.
    - Нет контроля доступа, шифрования, DLP, мониторинга.

#### Процесс 2: Приём у врача и обработка медицинских данных
- **Описание**: Врач просматривает журнал записей, запрашивает медицинские карты и анализы, создаёт заключения и рецепты. Данные хранятся в Excel и PDF/JPG на файловом сервере.
- **Конфиденциальные данные**: Медицинские данные, результаты анализов, рецепты.
- **Текущее состояние**:
    - Доступ к файлам без ролевого контроля.
    - Данные не тегированы как чувствительные.
    - Нет шифрования и аудита.
- **Соответствие требованиям**:
    - Нарушение конфиденциальности: врачи и другие сотрудники могут видеть все данные.
    - Нарушение целостности: возможны несанкционированные изменения.
    - Нарушение аудита: нет логов операций.
    - Нарушение шифрования: данные в Excel/PDF незащищены.
- **Соответствие практикам**:
    - Отсутствует классификация, шифрование, контроль доступа, DLP.

#### Процесс 3: Обработка платежей
- **Описание**: Пациент оплачивает услуги, кассир вносит данные в ККМ и Excel. Данные передаются в «1С Бухгалтерия» через TCP/IP-OLE.
- **Конфиденциальные данные**: Финансовые данные, банковские реквизиты, Ф. И. О.
- **Текущее состояние**:
    - Реквизиты записываются вручную, хранятся в Excel без защиты.
    - Передача данных через OLE не шифруется.
    - Нет аудита операций.
- **Соответствие требованиям**:
    - Нарушение конфиденциальности: доступ к данным в Excel для всех.
    - Нарушение целостности: возможны ошибки при ручном вводе.
    - Нарушение шифрования: данные не защищены при передаче.
    - Нарушение аудита: нет логов.
- **Соответствие практикам**:
    - Отсутствует классификация, шифрование, DLP, мониторинг.

#### Процесс 4: Учёт товарно-материальных ценностей (ТМЦ)
- **Описание**: Сотрудник склада вносит данные в «1С Торговля и склад», данные обмениваются с «1С Бухгалтерия» и хранятся на сервере.
- **Конфиденциальные данные**: Идентификаторы закупок (могут содержать данные поставщиков).
- **Текущее состояние**:
    - Доступ к данным без ролевого контроля.
    - Нет шифрования и аудита.
- **Соответствие требованиям**:

### Проблемные зоны
1. **Отсутствие классификации данных**:
    - Данные (персональные, медицинские, финансовые) не помечены как конфиденциальные, что затрудняет их защиту.
    - Нарушение Privacy by Design и ФЗ-152.

2. **Недостаточный контроль доступа**:
    - Доступ к данным ограничен только доменной аутентификацией, без RBAC/ABAC.
    - Все сотрудники с доступом к серверу могут просматривать и изменять данные.

3. **Отсутствие шифрования**:
    - Данные в Excel, PDF, JPG, «1С» и email не шифруются при хранении и передаче.
    - Нарушение конфиденциальности и целостности.

4. **Отсутствие аудита и Data Lineage**:
    - Операции с данными не логируются, невозможно отследить несанкционированный доступ.
    - Нарушение ФЗ-152 и ISO/IEC 27001.

5. **Ручная обработка данных**:
    - Ввод данных вручную увеличивает риск ошибок и утечек.
    - Отсутствие автоматизации для минимизации данных.

6. **Незащищённые email-уведомления**:
    - Уведомления содержат Ф. И. О., даты, результаты анализов без шифрования.
    - Риск перехвата и пересылки.

7. **Отсутствие DLP-систем**:
    - Нет механизмов предотвращения утечек данных (например, копирование файлов или отправка email).

8. **Несоответствие ФЗ-152**:
    - Нет механизмов удаления данных по запросу клиента.
    - Отсутствует классификация и защита данных, что влечёт штрафы.

9. **Отсутствие мониторинга и алертинга**:
    - Нет систем обнаружения аномалий или несанкционированного доступа.
    - Невозможно оперативно реагировать на инциденты.

10. **Физическая безопасность**:
    - Сервер находится в офисе без упоминания физической защиты (например, доступа к серверной комнате).

### Рекомендации
- Внедрить классификацию данных и тегирование.
- Настроить RBAC/ABAC для контроля доступа.
- Использовать шифрование (AES-256, TLS 1.3).
- Внедрить SIEM для аудита и мониторинга.
- Разработать DLP-системы для предотвращения утечек.
- Автоматизировать процессы для минимизации ручного ввода.
- Обеспечить физическую безопасность серверов.

### 2. Механизм тегирования данных и меры обеспечения конфиденциальности

#### Механизм тегирования
Тегирование классифицирует данные для защиты, контроля доступа и аудита, соответствуя ФЗ-152 и Privacy by Design.

##### Категории тегов
- **Тип данных**: `Personal`, `Medical`, `Financial`, `Employee`, `Contract`, `Notification`.
- **Чувствительность**: `High` (паспорт, диагнозы), `Medium` (Ф. И. О.), `Low` (обезличенные).
- **Контекст**: `Internal` (ресепшен, врачи), `External` (API, уведомления), `Analytics` (BI/ML).

##### Процесс тегирования
1. **Обнаружение**: Сканирование файлов (Excel, PDF) и систем («1С», Exchange) с шаблонами (например, паспорт: `\d{4}-\d{6}`).
2. **Классификация**: Автоматическое (`Personal:Medium` для email) и ручное (PDF с диагнозами) присвоение тегов.
3. **Присвоение**: Сохранение тегов в PostgreSQL или метаданных файлов.
4. **Контроль доступа**: RBAC/ABAC на основе тегов (например, `Medical:High` для врачей).
5. **Аудит**: Логирование операций с тегами в SIEM.

##### Инструменты тегирования (доступные в РФ)
- **Обнаружение и классификация**:
    - **Informatica Data Catalog**: Сканирование и тегирование (`Personal`, `Medical`).
    - **Varonis Data Classification Engine**: Обнаружение паспортов, СНИЛС.
- **DLP**:
    - **Symantec DLP**: Блокировка копирования (`Medical:High`).
    - **McAfee DLP**: Контроль передачи (`Financial:High`).
- **IAM**:
    - **Azure Active Directory**: RBAC для тегов (`Medical` для врачей).
    - **OneTrust**: Интеграция тегов с облаком.
- **SIEM**:
    - **Splunk**: Логирование операций с тегами.
    - **IBM QRadar**: Мониторинг аномалий.
- **Облачные метки**:
    - **Azure Information Protection**: Тегирование в облаке.

    - **Informatica**: Тегирование в базе.

    - **OneTrust**: Соответствие ФЗ-152.
